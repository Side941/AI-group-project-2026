# Known Issues — ICD-11 Knowledge Base (v1)

Two integrity defects exist in the current knowledge base
(`knowledge_base/icd_11/icd11_chunks.json`), plus one retrieval-behaviour
observation that affects how evaluation results should be read. None of them
break the pipeline — it runs and classifies — but they change *what* the
retrievers can return, how retrieved chunks are labelled in prompts, and how
many chunks actually reach the prompt, so they should be kept in mind when
interpreting evaluation results (particularly RQ1, RQ2 and RQ3).

Evidence for everything below is in `kb_snapshot_before.txt`, generated by
`scripts/kb_snapshot.py`, which inventories the chunk pool and shows the exact
retrieval results and prompt context blocks for one fixed sample query per
class. Re-running the script after any KB change produces a directly diffable
report. Claims not directly evidenced by that report are marked as such.

## Issue 1 — Mood episode descriptions attributed to 6A8Z

The CDDR mood chapter opens with descriptions of the four mood **episodes**
(Depressive, Manic, Mixed, Hypomanic) before the coded disorder entries.
These headings carry no ICD-11 code, so the chunker's code-tracking loop
attributed all of their content to the last code seen in the chapter's
category listing: **6A8Z "Mood disorder, unspecified"**.

Within the retrieval pool this is visible directly: 6A8Z holds 14 of the pool's
28 chunks (10 Essential Features, 4 Boundary with Normality), far more than any
genuine single disorder, and the ten Essential Features chunks group by content
into four blocks of 2/3/2/3 parts that correspond to the depressive, manic,
mixed and hypomanic episode descriptions respectively. (*The 2/3/2/3 mapping is
inferred from the chunk previews in the snapshot, not asserted by the
report itself.*)

The misattributed content includes the depressive-episode Essential Features,
i.e. the diagnostic criteria for a depressive episode **including the suicidal
ideation item** — the most task-relevant text in the entire knowledge base. In
the current KB it is labelled as an unspecified stub disorder, so any episode
chunk that is retrieved is presented to the LLM as
"(Mood disorder, unspecified — Essential Features)" rather than
"(Depressive episode — Essential Features)".

Part 3 of the snapshot shows this mislabelling in the prompt, but note *which*
chunk actually surfaces: for the suicidal-class query, entry [1] is the
**mixed**-episode text ("Several prominent manic and several prominent
depressive symptoms…"), not the depressive-episode criteria. The depressive
criteria never reach the prompt at all, because Issue 2 removes them first. The
two defects therefore compound rather than acting independently.

## Issue 2 — Chunk id collisions hide most of that content

Retriever-visible ids are built as `<disorder_code>_<section>` with no part
index, so every chunk sharing a (code, section) pair collapses to a single id.
De-duplication in the BM25 path then keeps one chunk per id and discards the
rest.

Combined with Issue 1 this is severe: all four episode types' Essential
Features chunks share the one id `6A8Z_essential_features` — **10 chunks
competing for a single retrievable slot** (depressive criteria vs manic vs
mixed vs hypomanic). The part carrying the suicidal ideation criteria loses
consistently: across all three sample queries the surviving `6A8Z` Essential
chunk is a `p1`, never the `p2` beginning "suicidal ideation (with or without a
specific plan)".

The snapshot lists the full collision groups: 3 colliding ids in the 28-chunk
retrieval pool hide 13 chunks, leaving 15 of 28 reachable — roughly half the
pool unreachable regardless of query.

*Scope caveat:* the snapshot run captured BM25 only, as the vector store was
absent (`NotFoundError: Collection [icd11_clinical] does not exist`). The dense
and hybrid paths share the same id-based de-duplication in code and so should be
affected identically, but that is an inference from the source, not an observed
result.

## Issue 3 — effective k exceeds the requested k under query expansion

Part 2 of the snapshot is run at k=5, but the default BM25 path returns 7, 9 and
8 chunks for the suicidal, depression and normal queries respectively. Only the
`expand=False` variant returns exactly 5. The Part 3 prompt block correspondingly
contains 7 numbered entries, not 5.

Query expansion is therefore inflating the number of chunks reaching the prompt
beyond the nominal k, by a variable amount that depends on the query. This
matters for RQ1: a k sweep over the default path is not comparing 5 vs 10 vs 20
retrieved chunks, it is comparing three inflated and query-dependent context
sizes, which partly confounds k with context length. Either report effective
chunk counts alongside nominal k, or run the sweep with expansion disabled and
treat expansion as a separate condition.

## Impact on current evaluation (RQ1–RQ4)

- Results on the current KB remain valid as the **v1 baseline** — the defects
  are constant across all configurations, so *relative* comparisons (k values,
  retrievers, prompting strategies) are still meaningful.
- RQ1 comparisons across k should be reported with effective chunk counts, per
  Issue 3, or with expansion held off.
- RQ3 interpretation needs care: where retrieved chunks look "useless or
  misleading", part of that may be an artifact of mislabelled and collapsed
  chunks rather than a property of ICD retrieval itself.
- RQ2 explanation grounding is affected in one specific way: the model cannot
  correctly attribute depressive-episode criteria to a named diagnostic
  entity — both because the KB names them "Mood disorder, unspecified" and
  because, in practice, it is usually a different episode's criteria that
  arrives under that label.

## Status and proposed path

A fix exists (episode headings detected and assigned pseudo-codes
`EP.DEP` / `EP.MAN` / `EP.MIX` / `EP.HYP`; globally unique `chunk_uid`
assigned at chunking time and used consistently by BM25/dense/hybrid), but it
requires regenerating the KB and re-ingesting the vector store, so it is
**deliberately not applied** while the current evaluation round is in
progress. The snapshot confirms it is unapplied: chunks carrying a `chunk_uid`
field: 0.

Proposal: finish the current evaluation on KB v1, then apply the fix as
**KB v2** and re-run the same evaluation. The v1-vs-v2 comparison directly
quantifies how much knowledge-base quality matters to the system — a strong
result for the report under RQ3 either way it comes out.
