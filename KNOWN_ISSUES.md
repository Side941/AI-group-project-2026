# Known Issues — ICD-11 Knowledge Base (v1)

Two integrity defects exist in the current knowledge base
(`knowledge_base/icd_11/icd11_chunks.json`). They do not break the pipeline —
it runs and classifies — but they change *what* the retrievers can return and
how retrieved chunks are labelled in prompts, so they should be kept in mind
when interpreting evaluation results (particularly RQ2 and RQ3).

Evidence for everything below is in `kb_snapshot_before.txt`, generated by
`scripts/kb_snapshot.py`, which inventories the chunk pool and shows the exact
retrieval results and prompt context blocks for one fixed sample query per
class. Re-running the script after any KB change produces a directly diffable
report.

## Issue 1 — Mood episode descriptions attributed to 6A8Z

The CDDR mood chapter opens with descriptions of the four mood **episodes**
(Depressive, Manic, Mixed, Hypomanic) before the coded disorder entries.
These headings carry no ICD-11 code, so the chunker's code-tracking loop
attributed all of their content — 42 chunks — to the last code seen in the
chapter's category listing: **6A8Z "Mood disorder, unspecified"**.

This content includes the depressive-episode Essential Features, i.e. the
diagnostic criteria for a depressive episode **including the suicidal ideation
item** — the most task-relevant text in the entire knowledge base. In the
current KB it is labelled as an unspecified stub disorder, so when it is
retrieved, the prompt presents it to the LLM as
"(Mood disorder, unspecified — Essential Features)" rather than
"(Depressive episode — Essential Features)". Part 3 of the snapshot report
shows this is what the model sees for a typical suicidal-class query.

## Issue 2 — Chunk id collisions hide most of that content

Retriever-visible ids are built as `<disorder_code>_<section>` with no part
index, so every chunk sharing a (code, section) pair collapses to a single id.
De-duplication in the BM25/dense/hybrid paths then keeps one chunk per id and
discards the rest.

Combined with Issue 1 this is severe: all four episode types' Essential
Features chunks share the one id `6A8Z_essential_features` — **10 chunks
competing for a single retrievable slot** (depressive criteria vs manic vs
mixed vs hypomanic), with the part containing the suicidal ideation criteria
usually losing. The snapshot report lists the full collision groups: 3
colliding ids in the 28-chunk retrieval pool hide 13 chunks, so roughly half
the pool is unreachable regardless of query.

## Impact on current evaluation (RQ1–RQ4)

- Results on the current KB remain valid as the **v1 baseline** — the defects
  are constant across all configurations, so *relative* comparisons (k values,
  retrievers, prompting strategies) are still meaningful.
- RQ3 interpretation needs care: where retrieved chunks look "useless or
  misleading", part of that may be an artifact of mislabelled and collapsed
  chunks rather than a property of ICD retrieval itself.
- RQ2 explanation grounding is affected in one specific way: the model cannot
  correctly attribute depressive-episode criteria to a named diagnostic
  entity, because the KB names them "Mood disorder, unspecified".

## Status and proposed path

A fix exists (episode headings detected and assigned pseudo-codes
`EP.DEP` / `EP.MAN` / `EP.MIX` / `EP.HYP`; globally unique `chunk_uid`
assigned at chunking time and used consistently by BM25/dense/hybrid), but it
requires regenerating the KB and re-ingesting the vector store, so it is
**deliberately not applied** while the current evaluation round is in
progress.

Proposal: finish the current evaluation on KB v1, then apply the fix as
**KB v2** and re-run the same evaluation. The v1-vs-v2 comparison directly
quantifies how much knowledge-base quality matters to the system — a strong
result for the report under RQ3 either way it comes out.
